[[configure-dns-for-air-gapped-host-discovery-in-netapp-console-local-deployment]]
== 在 NetApp Console 本地部署中为气隙主机发现配置 DNS

如果要在无法通过标准 DNS 访问数据库主机的空气隔离环境中使用 NetApp Console 本地部署，则需要临时修改内部 RKE2 CoreDNS 配置。这使 Pod 能够将特定主机名解析为集群中的 IP 地址，类似于在节点上向 `/etc/hosts`添加条目。


IMPORTANT: 在进行更改之前，请检查现有的 CoreDNS 配置和现有的 `rke2-coredns-config.yaml` HelmChartConfig，以避免覆盖任何现有的自定义配置。在大多数 NetApp Console 本地部署节点上，此文件已存在并已包含资源请求。如果文件已存在，请勿重新创建；而是仅将 `servers:`块附加到现有的 `valuesContent`中。请使用 RKE2 清单应用此更改，以便 RKE2 操作员和运行时继续对其进行统一管理。

.开始之前
* 在可能的情况下，将 HelmChartConfig 文件置于变更控制之下。
* 使用清晰的文件名，以便 CoreDNS 覆盖的目的显而易见。
* 如果预期的 DNS 记录在 Corefile 中不可见，请检查 RKE2 服务器日志并确认清单文件语法。


.步骤
. 检查现有 CoreDNS 配置，以确保未覆盖现有更改：
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
. 确认 HelmChartConfig 文件是否存在：
+
[source, shell]
----
sudo cat /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
+
[role="tabbed-block"]
====
.如果文件存在
--
.. 运行以下脚本，将 `servers:` 块追加到现有 HelmChartConfig 文件：
+
[source, shell]
----
MANIFEST=/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml

# 1. Back up first
sudo cp -a "$MANIFEST" "$MANIFEST.bak.$(date +%Y%m%d-%H%M%S)"

# 2. Safety checks: valuesContent must be the last key, no servers: block yet
grep -n 'servers:' "$MANIFEST"        # must return nothing
tail -c 1 "$MANIFEST" | od -c | head  # file must end with a newline

# 3. Append ONLY the servers block (nothing above it changes)
sudo tee -a "$MANIFEST" >/dev/null <<'YAML'
    servers:
    - zones:
      - zone: .
      port: 53
      plugins:
      - name: errors
      - name: health
        configBlock: |-
          lameduck 10s
      - name: ready
      - name: kubernetes
        parameters: cluster.local in-addr.arpa ip6.arpa
        configBlock: |-
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
          ttl 30
      # ───────────────────────── EDIT BELOW ─────────────────────────
      # Static DNS records for hosts the corporate DNS cannot resolve.
      # Format:  <IP>  <FQDN>  [optional aliases...]
      # `fallthrough` MUST stay as the last line -- it lets every other
      # name go to the upstream resolver via the `forward` plugin below.
      - name: hosts
        configBlock: |-
          1.2.3.4 example.domain.com exampleshortname
          fallthrough
      # ───────────────────────── EDIT ABOVE ─────────────────────────
      - name: prometheus
        parameters: 0.0.0.0:9153
      - name: forward
        parameters: . /etc/resolv.conf
      - name: cache
        parameters: 30
      - name: loop
      - name: reload
      - name: loadbalance
YAML

# 4. Confirm the merged result
sudo cat "$MANIFEST"
----
.. 验证 HelmChartConfig 文件的唯一更改是否是添加了 `servers:`块。


--
.如果文件不存在
--
.. 编辑以下脚本的 `configBlock`区域并添加静态 DNS 记录。这将在 RKE2 清单文件夹中创建一个 HelmChartConfig YAML 文件，RKE2 会自动应用该文件以覆盖 CoreDNS 配置：
+
[source, shell]
----
sudo tee /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml >/dev/null <<'YAML'
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-coredns
  namespace: kube-system
spec:
  # NOTE: This is a HelmChartConfig that *overlays* values onto the rke2-coredns
  # HelmChart already managed by RKE2. RKE2 watches /var/lib/rancher/rke2/server/manifests
  # and will re-render the rke2-coredns Helm release whenever this file changes.
  #
  # The `servers:` list below REPLACES the chart's default server definition,
  # so every plugin that was in the stock Corefile must be present here.
  # Do NOT delete plugins you don't recognize -- they are required for cluster DNS.
  valuesContent: |-
    servers:
    - zones:
      - zone: .
      port: 53
      plugins:
      - name: errors
      - name: health
        configBlock: |-
          lameduck 10s
      - name: ready
      - name: kubernetes
        parameters: cluster.local in-addr.arpa ip6.arpa
        configBlock: |-
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
          ttl 30
      # ───────────────────────── EDIT BELOW ─────────────────────────
      # Static DNS records for hosts the corporate DNS cannot resolve.
      # Format:  <IP>  <FQDN>  [optional aliases...]
      # `fallthrough` MUST stay as the last line -- it lets every other
      # name go to the upstream resolver via the `forward` plugin below.
      - name: hosts
        configBlock: |-
          1.2.3.4 example.domain.com exampleshortname
          fallthrough
      # ───────────────────────── EDIT ABOVE ─────────────────────────
      - name: prometheus
        parameters: 0.0.0.0:9153
      - name: forward
        parameters: . /etc/resolv.conf
      - name: cache
        parameters: 30
      - name: loop
      - name: reload
      - name: loadbalance
YAML
sudo chmod 600 /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
.. 复制并运行脚本。


--
====
. 验证 CoreDNS 是否已接受更改：
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
+
如果几分钟后无法看到更改，请重新启动 CoreDNS 部署，然后再次验证 Corefile：

+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----
. 如果需要在发现数据库主机后删除条目，请执行以下操作：
+
[role="tabbed-block"]
====
.如果附加到现有文件
--
.. 还原已备份的文件或仅从文件中删除 `servers:`块：
+
[source, shell]
----
sudo cp -a /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml.bak.<timestamp> \
/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
+
请勿删除此文件，因为它包含现有的 RKE2 资源优化。

.. 还原文件后，删除主机条目。过时的条目可能会导致主机发现和定时备份问题。
.. 重新启动 CoreDNS 部署：
+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----


--
.如果创建了新文件
--
.. 从清单文件夹中删除 HelmChartConfig 文件：
+
[source, shell]
----
sudo rm /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
.. 删除文件后，删除主机条目。过时的条目可能会导致主机发现和定时备份问题。
.. 重新启动 CoreDNS 部署：
+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----


--
====




[[discover-microsoft-sql-server-workloads-and-optionally-import-snapcenter-resources]]
== 发现 Microsoft SQL Server 工作负载并选择性地导入SnapCenter资源

在发现过程中，NetApp Backup and Recovery 会跨组织中的系统分析 Microsoft SQL Server 实例和数据库。

该服务评估现有保护级别，包括当前备份策略、快照以及备份和恢复选项。

发现以下列方式发生：

* 如果您已有SnapCenter ，请使用NetApp Backup and Recovery and Recovery UI 将SnapCenter资源导入NetApp Backup and Recovery and Recovery。
+

NOTE: 如果您已经拥有 SnapCenter，请在从 SnapCenter 导入之前，首先确认您已满足前提条件。例如，在从 SnapCenter 导入之前，您应将本地 SnapCenter 集群存储系统添加到 NetApp Console。请参见 link:concept-start-prereq-snapcenter-import.html["从SnapCenter导入资源的先决条件"]。

* 如果您还没有 SnapCenter，您仍然可以通过手动添加 vCenter 来发现工作负载并执行发现。




[[if-snapcenter-is-already-installed-import-snapcenter-resources-into-netapp-backup-and-recovery]]
=== 如果已安装SnapCenter ，请将SnapCenter资源导入NetApp Backup and Recovery

如果您已安装SnapCenter ，请按照以下步骤将SnapCenter资源导入NetApp Backup and Recovery 。  NetApp Console从SnapCenter发现资源、主机、凭据和计划；您不必重新创建所有这些信息。

您可以通过以下方式执行此操作：

* 在发现期间，选择一个选项从SnapCenter导入资源。
* 发现后，从“清单”页面选择一个选项来导入SnapCenter资源。
* 发现后，从“设置”菜单中选择一个选项来导入SnapCenter资源。有关详细信息，请参阅link:br-start-configure.html["配置NetApp Backup and Recovery"]。


这是一个由两部分组成的过程：

* 导入SnapCenter Server 应用程序和主机资源
* 管理选定的SnapCenter主机资源




==== 导入SnapCenter Server 应用程序和主机资源

第一步从SnapCenter导入主机资源并在NetApp Backup and Recovery清单页面中显示这些资源。此时，资源尚未由NetApp Backup and Recovery管理。


TIP: 导入SnapCenter主机资源后， NetApp Backup and Recovery不会自动接管保护管理。为此，您必须明确选择在NetApp Backup and Recovery中管理导入的资源。这可确保您已准备好通过NetApp Backup and Recovery备份这些资源。

.步骤
. 从NetApp Console左侧导航中，选择 *保护* > *备份和恢复*。
. 选择*库存*。
. 选择*发现资源*。
. 从NetApp Backup and Recovery Discover 工作负载资源页面中，选择 *从SnapCenter导入*。
. 输入* SnapCenter应用程序凭据*：
+
.. * SnapCenter FQDN 或 IP 地址*：输入SnapCenter应用程序本身的 FQDN 或 IP 地址。
.. *端口*：输入SnapCenter服务器的端口号。
.. *用户名*和*密码*：输入SnapCenter服务器的用户名和密码。
.. *控制台代理*：选择SnapCenter的控制台代理。


. 输入* SnapCenter服务器主机凭据*：
+
.. *现有凭证*：如果选择此选项，则可以使用已添加的现有凭证。选择凭证名称。
.. *添加新凭据*：如果您没有现有的SnapCenter主机凭据，则可以添加新凭据。输入凭证名称、身份验证模式、用户名和密码。


. 选择“*导入*”来验证您的条目并注册SnapCenter服务器。
+

NOTE: 如果 SnapCenter 服务器已注册，您可以更新现有的注册详细信息。



.结果
"清单"页面显示导入的 SnapCenter 资源，其中包括 Microsoft SQL Server 主机、实例和数据库。

要查看导入的SnapCenter资源的详细信息，请从“操作”菜单中选择“查看详细信息”选项。



==== 管理SnapCenter主机资源

导入 SnapCenter 资源后，在 NetApp Backup and Recovery 中管理主机资源。选择管理这些资源后，NetApp Backup and Recovery 可以备份和恢复导入的资源。您不再在 SnapCenter Server 中管理这些资源。

.步骤
. 导入SnapCenter资源后，从备份和恢复菜单中选择*Inventory*。
. 在“清单”页面中，选择已导入的 SnapCenter 主机，以便由 NetApp Backup and Recovery 进行管理。
. 选择“操作”图标image:../media/icon-action.png["操作选项"]> *查看详情*显示工作量详情。
. 在清单 > 工作负载页面中，选择操作图标image:../media/icon-action.png["操作选项"]> *管理* 显示管理主机页面。
. 选择*管理*。
. 在管理主机页面中，选择使用现有 vCenter 或添加新的 vCenter。
. 选择*管理*。
+
库存页面显示新管理的SnapCenter资源。



您可以选择从“操作”菜单中选择“生成报告”选项来创建管理资源的报告。



==== 从清单页面发现后导入SnapCenter资源

如果您已经发现资源，则可以从清单页面导入SnapCenter资源。

.步骤
. 从控制台左侧导航中，选择*保护*>*备份和恢复*。
. 选择*库存*。
. 从库存页面中，选择*导入SnapCenter资源*。
. 按照上面“导入SnapCenter资源”部分中的步骤导入SnapCenter资源。




[[if-you-dont-have-snapcenter-installed-add-a-vcenter-and-discover-resources]]
=== 如果您尚未安装SnapCenter ，请添加 vCenter 并发现资源

如果尚未安装 SnapCenter，则可以添加 vCenter 信息并让 NetApp Backup and Recovery 发现工作负载。在每个 Console 代理中，选择要发现工作负载的系统。

如果您有 VMware 环境，则此步骤为可选步骤。

.步骤
. 从控制台左侧导航中，选择*保护*>*备份和恢复*。
+
如果您是第一次登录备份和恢复，并且在控制台中有一个系统但没有发现任何资源，则会显示“欢迎使用新的NetApp备份和恢复”页面，其中包含“发现资源”选项。

. 选择*发现资源*。
. 输入以下信息：
+
.. *工作负载类型*：对于此版本，仅 Microsoft SQL Server 可用。
.. *vCenter 设置*：选择现有的 vCenter 或添加新的 vCenter。要添加新的 vCenter，请输入 vCenter FQDN 或 IP 地址、用户名、密码、端口和协议。
+

TIP: 如果要输入 vCenter 信息，请输入 vCenter 设置和主机注册信息。如果您在此处添加或输入了 vCenter 信息，则还需要在接下来的高级设置中添加插件信息。

.. *主机注册*：选择*添加凭据*并输入包含您想要发现的工作负载的主机的信息。
+

TIP: 如果要添加独立服务器而不是 vCenter 服务器，则仅输入主机信息。



. 选择*发现*。
+

TIP: 此过程可能需要几分钟。

. 继续高级设置。




==== 在发现期间设置高级设置选项并安装插件

使用高级设置，您可以在所有注册的服务器上手动安装插件代理。这使您能够将所有 SnapCenter 工作负载导入 NetApp Backup and Recovery，以便您可以在其中管理备份和还原。NetApp Backup and Recovery 显示安装插件所需的步骤。

.步骤
. 在"发现资源"页面中，选择右侧的向下箭头，继续进入"高级设置"。
. 在发现工作负载资源页面中，输入以下信息。
+
** *输入插件端口号*：输入插件使用的端口号。
** *安装路径*：输入将安装插件的路径。


. 如果要手动安装 SnapCenter 代理，请选择以下选项：
+
** *Use manual installation*：选择此选项可手动安装插件。
** *添加集群中的所有主机*：选择此选项可在发现期间将集群中的所有主机添加到 NetApp Backup and Recovery。
** *跳过可选的安装前检查*：选择此选项可跳过可选的安装前检查。例如，如果您知道内存或空间方面的考虑因素将在不久的将来发生变化，并且想要立即安装插件，则可能需要执行此操作。


. 选择*发现*。




==== 继续访问NetApp Backup and Recovery仪表板

. 在 NetApp Console 菜单中，选择*保护* > *备份和恢复*。
. 选择一个工作负载图块（例如，Microsoft SQL Server）。
. 从备份和恢复菜单中，选择*仪表板*。
. 查看数据保护的运行状况。根据新发现、受保护和备份的工作负载，高风险或受保护工作负载的数量会增加。
+
link:br-use-dashboard.html["了解仪表板显示的内容"]。
